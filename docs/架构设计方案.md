# 技术架构方案：后厨出品与前厅协作智能体系统

> 按「四层架构」模板输出；领域对象映射：报销制度知识库 → 工艺卡/菜品知识库，员工/管理员 → 前厅档口员工 / 管理员。
> 约束：FastAPI（异步）、Python 3.11+、LLM 走 API 可换供应商、知识库向量化检索。
> 事实依据：《业务需求发现报告》（36 条事实、REQ-1~6）与《业务挖掘报告》。

---

## ① 四层架构图

```
┌─ 入口层 ──────────────────────────────────────────────┐
│  员工端 Web            管理员端 Web         FastAPI 路由 │
│ （点单·看板·问答）   （知识库维护·记录）    （REST·异步）  │
└──────────────────────┬────────────────────────────────┘
┌─ 服务层 ──────────────▼────────────────────────────────┐
│  认证鉴权(JWT)   订单·看板服务   知识库服务   审计留痕服务 │
└──────────────────────┬────────────────────────────────┘
┌─ 智能体编排层 ─────────▼────────────────────────────────┐
│                 编排器（事件总线）                       │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐   │
│  │ 解析Agent │ │ 校验Agent │ │ 调度Agent │ │ 通知Agent │   │
│  │LLM可换供应商│ │过敏BLOCK │ │计分排菜   │ │催菜·异常  │   │
│  │+规则兜底   │ │级拦截    │ │输出排序理由│ │提示      │   │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘   │
│   置信度 < 阈值 → 人工修复队列（不进自动流）               │
└──────────────────────┬────────────────────────────────┘
┌─ 数据模型层 ──────────▼────────────────────────────────┐
│  PostgreSQL（业务+审计）   pgvector（向量检索）   文件存储  │
└────────────────────────────────────────────────────────┘
```

**层间职责边界**（答辩/评审时讲清楚的三句话）：
1. 入口层只做协议转换，不含业务逻辑；
2. 智能体编排层只消费/产生**事件**，服务层不直接调用具体 Agent——换掉任何一个 Agent 不影响其余链路；
3. LLM 只出现在解析 Agent 内部，通过 Provider 抽象隔离，**任何供应商故障都降级到规则解析**，正确性不依赖 LLM（对应发现报告"只读优先、过敏不可先自动处理"的红线）。

## ③ 数据库表设计（PostgreSQL + pgvector）

| 表 | 关键字段 | 说明 |
|----|---------|------|
| **users** | id, username, password_hash, role(`employee`/`admin`), station, is_active | 双角色；station 关联档口权限 |
| **kb_documents** | id, title, doc_type(工艺卡/制度), file_path, version, status(`draft`/`published`), updated_by, updated_at | 知识库文档，版本化——管理员发布才对员工可见 |
| **kb_chunks** | id, doc_id→kb_documents, chunk_index, content, embedding `vector(1536)` | 向量检索的最小单元；文档更新即重建 chunks |
| **dishes** | id, name, station, standard_minutes, version, is_active | 工艺卡结构化字段（制作时间等），与文档互补 |
| **orders** | id, biz_no(业务编号), source(`paper`/`system`/`voice`), table_no, status, raw_text, created_by, created_at, closed_at | biz_no 贯穿全链路留痕；source 支持纸质单归一 |
| **order_items** | id, order_id→orders, dish_id, qty, notes, allergy_flag, status | 拆单后**过敏标志随行传递**（对应对应痛点） |
| **board_tasks** | id, order_item_id, station, score, reason, status(`queued`/`cooking`/`done`), urge_count, snapshot_at | reason 存排序理由（可解释）；snapshot 支持复盘 |
| **repair_queue** | id, source_event_id, reason, assigned_to, deadline_at, resolved_at, status | 人工修复队列——低置信度/BLOCK 触发，责任人+时效 |
| **events** | id, biz_no, event_type, payload `JSONB`, actor_id, created_at | **只追加**事件流，全程留痕可重建处理链 |

**设计要点**：
- 三套"完成"口径统一落点：`orders.status` 状态机是唯一判定源，前厅/后厨/顾客视角只是它在不同入口的投影；
- `events` 与 `repair_queue` 直接回应发现报告中"留痕自动生成还是人工补录、修复队列责任人时效"两个未核实项——系统侧自动生成，人工只做确认；
- 向量列用 pgvector 而非独立向量库：单店规模没必要多养一个组件。

## ④ 第一周最小验证目标

| 天 | 目标 | 完成标志 |
|----|------|---------|
| D1–D2 | FastAPI 骨架 + users 表 + JWT 登录 | 两个角色分别登录，访问各自受限接口返回 200/403 正确 |
| D3 | 知识库链路：上传工艺卡文档 → 切分向量化入库 → 检索问答接口 | 用自然语言问"红烧肉的标准制作时间"，返回正确答案与出处文档 |
| D4 | 订单链路：下单 API → 校验 Agent（过敏 BLOCK）→ 事件留痕 | 带过敏备注的订单被拦截，`events` 表可查到完整记录 |
| D5 | 调度链路：计分排菜 + 看板只读接口 + 排序理由 | 看板返回带 reason 的有序任务列表 |

**周末验收口径（两条路径 + 一条降级）**：
1. **拦截路径**：提交带过敏备注的套餐拆单 → 返回 BLOCK + `repair_queue` 生成待办 → 管理员在记录页可见；
2. **正常路径**：普通订单 + 一次催菜 → 看板顺序变化且每条带理由；
3. **降级路径**：拔掉 LLM Key 重跑解析 → 规则兜底生效，置信度封顶标记，流程不中断。

三条都绿，第一周即宣告"骨架可信"，第二周再补真实文档批量入库与员工端页面。
